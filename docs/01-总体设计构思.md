# 01 总体设计构思

> 文档定位：回答"我们要做什么、为谁做、怎么做才有价值"。后续所有技术文档都服务于本节的目标与原则。

## 1. 背景

传统文物的数字化在国内已有多年积累：三维扫描、摄影测量、光谱分析、病害检测等技术在博物馆与考古单位已常态化应用。但现状存在几个结构性问题：

- **成果分散**：数字化成果沉淀在各馆、各项目、各服务商手里，数据格式与元数据标准不统一，跨馆难以互通互认；
- **生命周期无可信记录**：一件文物从采集、修复到再采集，"哪个版本最新、哪个版本权威、改动过什么"缺乏不可抵赖的记录；
- **真伪不可自证**：数字影像与三维模型被复制传播后，无法证明来源与完整性；
- **授权边界模糊**：数字资源的版权归属、使用范围、收益分配缺乏机制；
- **公众信任缺失**：公众无法验证"网上看到的文物数字图像是否官方、是否被篡改"。

**本项目不重复建设采集能力**，而是在现有数字化成果之上，补一层**信任基础设施**：用区块链把"谁、在何时、对哪件文物、做了什么、产出物指纹是什么"变成不可篡改的事实记录。

## 2. 痛点与对策

| # | 痛点 | 现状 | 区块链对策 |
| --- | --- | --- | --- |
| P1 | 数据孤岛 | 各馆各自建档 | 联盟链统一登记标准，机构签名背书，跨馆互认 |
| P2 | 篡改无痕 | 数字文件可无限复制 | 内容哈希上链，任何人可离线验证完整性 |
| P3 | 溯源断裂 | 修复/流转记录散落 | 溯源事件链，只增不改 |
| P4 | 授权不清 | 数字资源使用无契约 | 授权合约记录对象、范围、期限、收益 |
| P5 | 访问失控 | 高精度模型流向不明 | 数据分级 + 访问审计上链 |
| P6 | 公众不信任 | 无法自证真伪 | 公众端"验证入口"，哈希比对一键可查 |

## 3. 设计目标

| 目标 | 含义 | 可验证标准（示例） |
| --- | --- | --- |
| G1 可验证 | 任何数字文件可证明来源与完整性 | 输入文件即可返回"官方/未知/被篡改"结论 |
| G2 可溯源 | 文物全生命周期事件可查 | 任意事件可在秒级完成链上核验 |
| G3 可互认 | 跨馆统一标识与元数据 | 新机构接入无需改造既有系统 |
| G4 可授权 | 数字资源授权全程留痕 | 每次授权可审计、可撤销 |
| G5 可运营 | 低成本、易接入 | 中小馆也能以极低门槛接入 |

## 4. 核心概念模型

### 4.1 名词定义

| 概念 | 定义 |
| --- | --- |
| 文物 Relic | 实体文物，以馆藏编号唯一标识 |
| 数字孪生 Twin | 文物在数字世界的唯一对应对象，1 件文物对应 1 个孪生 |
| 版本 Version | 孪生在某一时点的数据快照（修复、再采集后产生新版本） |
| 数字文件 AssetFile | 三维模型、影像、光谱数据、文档等具体文件 |
| 溯源事件 Event | 鉴定、检测、修复、借展等事实的记录 |
| 授权 License | 对某孪生/某版本/某文件的使用许可 |
| 身份 DID | 机构/个人的去中心化身份标识 |
| 可验证凭证 VC | 鉴定证书、检测报告等可机器验证的证书 |

### 4.2 关系示意

```
                ┌─────────────────────────────┐
                │        实物文物 Relic        │
                └──────────────┬──────────────┘
                               │ 1:1
                ┌──────────────▼──────────────┐
                │        数字孪生 Twin         │
                └──────┬───────────────┬──────┘
                 1:n   │               │ 产生
                ┌──────▼──────┐   ┌────▼──────────────────────┐
                │ 版本 Version │   │ 溯源事件 Event（链上）      │
                └──────┬──────┘   │  - 鉴定/检测/修复/借展...   │
                 1:n   │          │  - 机构DID签名 + 证据哈希   │
                ┌──────▼────────┐ └───────────────────────────┘
                │ AssetFile     │
                │ （链下存储）   │◄──── 授权 License（链上）
                └───────────────┘
```

## 5. 角色与权限

| 角色 | 典型主体 | 关键能力 |
| --- | --- | --- |
| 主管部门 | 省/市文物局 | 治理参与、标准制定、审计监督 |
| 馆藏单位 | 博物馆 | 创建孪生、提交登记、发布新版本、发起授权 |
| 鉴定检测机构 | 检测中心、实验室 | 签发检测报告 VC、记录检测事件 |
| 修复团队 | 修复室、高校 | 记录修复事件、提交修复后新版本 |
| 研究机构 | 高校、研究院 | 申请授权、使用数字资源 |
| 公众 | 观众、爱好者 | 查询验证、浏览公开数据、（可选）持有数字藏品 |
| 平台运营方 | 项目团队 | 系统运维、机构接入、技术支持 |

## 6. 核心业务流程

### 6.1 采集登记

```
三维扫描/摄影测量 → 质量审核 → 文件哈希计算 → 馆藏单位签名 → 链上登记
                                                                      │
                                                        对外可验证（任何人可核）
```

### 6.2 检测/修复溯源

```
发起工单 → 执行检测/修复 → 机构 DID 签名事件 + 证据哈希 → 链上追加
                                                              │
                                         若文物数据变化 → 登记新版本（旧版本保留）
```

### 6.3 数字资源授权

```
申请 → 馆藏单位审批 → 授权合约记录（对象/范围/期限/费用）→ 交付加密包 → 使用留痕
```

### 6.4 公众验证

```
获得数字文件 → 本地计算哈希 → 与链上登记记录比对 → 结论：官方原版/被篡改/未登记
```

## 7. 设计原则

1. **链上最小化**：链上只存哈希、状态与关键事实；大文件一律链下存储；
2. **权威背书**：区块链保证"记录不可篡改"，但不解决"源头真假"——源头真实性由权威机构签名与流程约束保障；
3. **分层开放**：L0/L1 高精度数据仅机构可见，公众看 L2/L3 展示级版本；
4. **标准优先**：元数据、DID、VC 采用开放标准（见 03 文档），避免厂商锁定；
5. **可演进**：业务层通过链适配层隔离具体链实现，未来可换链、可跨链；
6. **合规先行**：数据分类分级、跨境、数字藏品边界从设计第一天纳入（见 05 文档）。

## 8. 非目标（本期明确不做）

- 不交易文物实物（依法禁止的范畴绝不触碰）；
- 不炒作无授权的文物 NFT（数字藏品方向单独合规论证）；
- 不替代博物馆现有藏品管理系统（做集成与锚定）；
- 不追求高吞吐（文物场景是低频高价值写入，对 TPS 几乎无要求）。
